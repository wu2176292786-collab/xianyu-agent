# 选品判断层 · 三项增量 · 执行计划

> 这一版解决的问题：**让模型在「选品」上多出力，但一步都不碰采集层。**
>
> 采集层（限速队列 + 浏览器旁听 mtop 响应）已经跑通并验证过，它的价值恰恰在于
> 节奏可控：一轮 6 件、件间随机 4–9 秒、30 分钟冷却、每日 60 件预算。
> 这三项增量全部在数据**已经到手之后**才开始工作。

## 1. 边界：为什么模型不参与拉取

对标 `Usagi-org/ai-goofish-monitor`（14.3k star，2026-06-09 已归档）的做法：
它的拉取是纯 Playwright，AI 只出现在两个位置 —— 建任务时把一句话变成分析标准，
以及逐件商品做多模态筛选。**"搜什么"是人定的，"怎么翻页"是确定性代码，
"这件值不值得看"才是模型。**

我们沿用同一条分界线，理由不是能力问题：

- 模型没有我们的闲鱼会话。拉数据必须落到「浏览器 + 登录 cookie + 页面自己算签名」
  这条链上，模型最多是在链上按按钮。
- 避风控最要紧的是节奏可控。换成模型决定「现在拉哪几件、拉几件」，
  节奏就变成不可预测的 —— 那是拿最不该赌的东西去赌。
- 成本上也不划算：判断「这件今天要不要采」一行 `shopDay(last) !== shopDay(now)` 就够了。

所以下面三项的共同约束：**只读已入库的数据，不发起任何对闲鱼的请求。**

## 2. 三项增量

| 编号 | 名称 | 解决什么 | 新增面 |
| --- | --- | --- | --- |
| A | 多模态筛选 | 同款判断只看标题正文会错，关键信息在图里 | 改一个函数 + 一个环境变量 |
| B | 自然语言建任务 | `mustInclude` / `mustExclude` 要手填，门槛高 | 一个 LLM 函数 + 对话框一个输入框 |
| C | Agent 读取工具 | 拿到数据之后没人替你读，趋势要自己一行行对 | 一组只读工具 + 一个问答入口 |

建议顺序 **B → A → C**：B 最小最低风险，A 对选品质量影响最大，C 新增面最大、需要额外的
数字护栏。三项互不依赖，也可以单独做。

## 3. A · 多模态筛选

### 3.1 现状

`screenRivalCandidates()`（`src/lib/agent/llm.ts:370`）把本店标题正文 + 候选的标题正文
拼成一段纯文本发给模型，返回 `keepIds`。解析失败回落到关键词规则
（`ruleKeepItemIds`），这条链已经在 `screenAndPruneRivals()` 里跑着。

图一张都没发。而闲鱼上判断同款、成色、有没有水印，很多线索只在图里。

### 3.2 改法

**请求体从字符串换成分段数组。** OpenAI 兼容接口的 `content` 支持
`[{type:"text"},{type:"image_url"}]`，改的是 `messages[1].content` 的构造，
接口调用和解析都不动。

**只发封面。** 每个候选取 `displayImageUrls(rival.imageUrls)[0]`。
多发几张对同款判断的边际收益低，token 成本却是线性的。

**先文字后图，只对存疑的看图。** 这是省钱的关键：
1. 先跑现有的纯文字筛选，拿到 keep / drop；
2. 把模型明确 drop 且理由是"拿不准"的那些挑出来（需要 prompt 多返回一个
   `reason: "sure" | "unsure"` 字段）；
3. 只对 unsure 的那一批发第二轮带图请求。

第一版可以先不做这个优化，全量带图，但要先加 **分批**：图会让单次请求变大，
按 8 个候选一批切开，逐批调用再合并 `keepIds`。

**视觉模型单独配。** `llmStatus()` 现在只有一个 `model`，它同时用于回复润色、
文案润色、对照分析 —— 那些场景不需要视觉，强制换成多模态模型只会更贵更慢。
新增可选环境变量：

```
OPENAI_VISION_MODEL=   # 留空 = 不看图，退回纯文字筛选
```

`llmStatus()` 增加 `visionModel?: string`；`screenRivalCandidates` 只有拿到它才带图。

**回落链变成三级**：带图筛选 → 纯文字筛选 → 关键词规则。任何一级失败都往下退，
不阻塞入库。

### 3.3 风险

**图链可能取不到。** 模型服务端去拉 `img.alicdn.com`，可能因为
来源限制或网络拉不到。真出现的话降级方案是本地下载再转 base64 内联
（`data:image/jpeg;base64,...`），代价是请求体大得多，所以不作为第一版方案。
第一版要做的是：带图请求失败时**明确记一条日志说明是图的问题**，不要静默退回。

**token 成本。** 一张封面按 `detail: "low"` 大约 85 token，8 个候选一批约 700 token，
可以接受。必须在请求里显式写 `detail: "low"`，默认的 `auto` 会按原图尺寸计费。

### 3.4 验收

- 配了 `OPENAI_VISION_MODEL` 时，请求体里有 `image_url` 分段，且 `detail: "low"`
- 没配时行为和现在完全一致（回归测试锁住）
- 候选超过 8 个时切成多批，`keepIds` 合并且不重复
- 带图调用失败时日志里能看出是图的问题，且结果和纯文字筛选一致
- 单元测试用注入的 `fetchImpl` 断言请求体形状，不打真实接口

## 4. B · 自然语言建任务

### 4.1 现状

`research-task-dialog.tsx` 让你手填「你准备在闲鱼搜的词」「必须含」「必须不含」。
这三个字段决定了 `alignmentFor()` 怎么判可比，填不好整个任务就偏。

### 4.2 改法

**新增 `draftTaskRules()` 到 `llm.ts`。** 输入一句话（可选附上对标的本店商品标题正文），
输出：

```ts
interface TaskRuleDraft {
  name: string;
  keyword: string;
  mustInclude: string[];
  mustExclude: string[];
}
```

**输出是草稿，不是结果。** 模型填完直接塞进对话框的表单里，你改完再点创建。
这条是刻意的：仓库里已有的原则是「人看过的结论比关键词可靠」
（`alignmentBy: "human"` 不被自动判定覆盖），建任务这一步同样不该让模型拍板。

**护栏。** 和 `judgePolished()` 同一套思路 —— 宁可弃用也不放行半残的输出：
- 四个字段齐全、都是字符串 / 字符串数组，否则整份弃用
- `keyword` 非空且不超过 30 字
- `mustInclude` / `mustExclude` 各最多 6 个词，单词不超过 12 字，去重、去空
- 两个数组不能有交集（既必须含又必须不含是自相矛盾的输出）
- 任何一条不过就返回 `null`，UI 提示"模型没给出可用的规则，请手填"

**UI。** 对话框顶部加一个 textarea「用一句话说你想找什么」+ 一个「让模型填」按钮。
点了之后按钮进 pending，填充成功就把三个字段写进表单并 toast 说明"这是草稿，
确认后再创建"。没配 `OPENAI_API_KEY` 时按钮置灰并说明原因。

### 4.3 验收

- 一句话「我想找卖 AI 智能体课程的，不要卖教材和书的」能生成可用的三个字段
- 生成的内容进表单、可编辑，不会绕过表单直接建任务
- 模型返回残缺 JSON、空数组、两数组有交集时都不写入表单，提示手填
- 没配模型时按钮置灰
- 单元测试覆盖护栏的每一条拒绝路径

## 5. C · Agent 读取工具

### 5.1 现状

`src/lib/agent/pi/tools.ts` 只有 `survey_shop` 和 `select_proposals` 两个工具，
作用域是本店运营（待回复、擦亮、降价、备货、下架），跑在巡检循环里，
协议很严：必须先 survey 再 select，不能发明编号。

选品这边的数据没有对应的工具。想知道「这家店最近在降价抢量」，现在只能自己一行行对表格。

### 5.2 改法

**新建 `src/lib/agent/pi/research-tools.ts`，四个只读工具**，全部搭在
`analysis.ts` 现成的纯函数上，不新增任何数据获取：

| 工具 | 返回 | 底层 |
| --- | --- | --- |
| `list_research_tasks` | 任务清单：名称、类型（关键词/店铺）、货件数 | 直接读 state |
| `price_band(taskId)` | 最低 / 中位 / 最高价，只算规格可比的 | `priceBand()` |
| `shop_pulse(taskId)` | 逐件：现价、上次价、价差、想要和浏览的日对比 | `dailyCompare()` + 观察时间线 |
| `rival_heat(rivalId)` | 单件的观察时间线和增速 | `wantsTrend()` / `viewsTrend()` |

**入口不挂在巡检循环上。** 巡检那个 agent 的协议是「survey → select」，
塞进读取工具会把它的行为搞乱。做成研究页上一个独立的问答框：
你打一个问题 → server action 起一个 pi Agent（带这四个工具）→ 返回一段文字。

**数字护栏是这一项的核心。** 自由文本输出最容易编数字，而这个项目的底线是
「材料里没有的数字不能出现」（`RESEARCH_SYSTEM_PROMPT` 已经这么要求，但只靠 prompt）。
做法是把它变成可执行的校验：

1. 每个工具返回时，把返回文本里的所有数字收进一个集合（复用 `llm.ts` 里的 `numbersIn()`）；
2. agent 给出最终回答后，抽出回答里的所有数字；
3. 有任何一个不在集合里 → **整段弃用**，回复"模型给的数字对不上材料，这一轮不显示"。

这和 `judgePolished()` 拦编造价格是同一个机制，已经在仓库里证明过有效。

**其他约束。** 45 秒超时（和 `PI_TIMEOUT_MS` 一致）；不能写状态，所有工具只读；
问答结果不进 `activity`（那是动作日志，不是聊天记录）。

### 5.3 风险

**这是新增面最大的一项。** 一个自由问答框意味着不可预测的 token 消耗和不可预测的输出。
数字护栏能挡住编数字，挡不住"解释得似是而非"。所以第一版建议：
- 答案上方永远显示"以下由模型根据库里的观察生成，数字已校验"
- 每次回答附上它调了哪些工具（`survey_shop` 的做法已经有先例）

### 5.4 验收

- 四个工具都不写状态，也不发起任何对闲鱼的请求
- 问"这家店最近在降价吗"时，agent 会调 `shop_pulse` 而不是凭空回答
- 人为让模型输出一个材料里没有的数字时，整段被弃用
- 超时、模型没配、工具报错时都有明确提示，不是空白
- 单元测试用假的 stream 驱动 agent，断言工具调用序列和数字护栏

---

## 6. 明确不做

- 让模型决定采集节奏（哪几件、什么时候、几件一轮）
- 让模型看图猜想要或浏览 —— 数字只认接口和页面上抽出来的字段
- 根据同行数据自动改本店标题、主图、价格（改动必须人工确认）
- 把问答结果当成动作写进行动队列

## 7. 一次性前置

A 项需要在 `.env.local` 加 `OPENAI_VISION_MODEL`；不加则 A 项静默不生效，
其余两项不依赖新配置。
