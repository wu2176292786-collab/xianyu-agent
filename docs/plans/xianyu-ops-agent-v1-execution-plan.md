## 1. 要解决的问题

闲鱼卖家的日常是碎片化的重复劳动：

- 商品挂久了沉底，需要不停擦亮、阶梯降价；
- 买家消息集中在晚上，议价、问参数、催发货混在一起，回复慢就掉单；
- 付款后有发货时效承诺，超时会影响店铺体验分；
- 卖掉的东西忘了下架，造成超卖纠纷。

这些事都有明确规则，但没人愿意一天做十遍。v1 的目标是把它们交给一个**带审批的 Agent**：
它负责发现问题、给出带理由的建议，人负责点头。

## 3. 架构

```
浏览器 ──► Next.js App Router（Server Components + Server Actions）
                 │
                 ├── 规则引擎 proposeActions()  纯函数：状态 + 时间 → 建议
                 ├── 回复起草 draftReply()      纯函数：会话 + 商品 + 设置 → 草稿
                 │        └── 可选 LLM 润色（配了 OPENAI_API_KEY 才走）
                 ├── 平台适配层 XianyuAdapter   v1 = MockXianyuAdapter
                 └── 存储 .data/state.json      单进程串行读写
```

### 3.1 领域模型（`src/lib/domain/types.ts`）

`Listing`、`Conversation` / `Message`、`Order`、`AutomationRule`、`AgentAction`、
`ActivityEntry`、`DailyMetric`、`ShopSettings`。金额一律以**分**为单位存储。

`AgentAction` 是整个产品的核心对象：它带着 `title`、`reason`（为什么提出来）、
`risk`（低 / 涉及金额 / 需谨慎）、`payload`（要执行的具体动作）和 `status`。

### 3.2 规则引擎（`src/lib/agent/engine.ts`）

`proposeActions(state, now)` 是纯函数，输出 `Proposal[]`：

| 规则 | 触发条件 | 默认是否需要审批 |
| --- | --- | --- |
| 定时擦亮 | 在售 + 有库存 + 距上次擦亮 ≥ N 小时，按最旧优先取前 K 个 | 否，自动执行 |
| 滞销降价 | 在售 + 上架 ≥ N 天 + 7 天浏览 ≤ 阈值 + 当前价 > 底价 | 是 |
| 自动回复 | 会话未关闭且最后一条是买家消息 | 是 |
| 超时备单 | 订单待发货且付款超过承诺时效 | 是 |
| 零库存下架 | 库存 = 0 但状态仍是在售 | 否，自动执行 |

两条安全约束写死在引擎里：

1. **降价永不低于商品底价**（`floorPriceCents`），适配层会二次拦截；
2. **低置信度或需要人工核实的回复草稿强制进审批队列**，即使规则设成了自动执行。

`runTick(state, adapter, now, trigger)` 负责编排：产生提案 → 免审批的直接执行 →
其余入队 → 失败的标成 `failed` 并留下原因 → 刷新会话意图标签 → 记录 `lastTickAt`
和一条巡检记录。已在队列中的同类动作不会被重复提出。

### 3.3 平台适配层（`src/lib/adapters/`）

读写分成两个接口：

- `XianyuReader.fetchSnapshot()` 把平台上的商品、会话、订单拉回来；
- `XianyuAdapter` 定义五个写操作：擦亮、改价、下架、发消息、发货。

分开的意义在于支持**混合模式**：读真实数据 + 写模拟，在自己真实店铺的数据上验证
规则靠不靠谱，同时一个字都不往平台上写。

v1.2 实现了两侧的模拟通道。模拟读通道不是把本地数据原样还回来 —— 那样同步永远是
空操作、合并逻辑也没机会被验证 —— 而是造出平台侧本来就会有的变化：曝光在涨、偶尔
来一条新消息、偶尔多一笔订单。

所有写操作都必须穿过 `GuardedAdapter`，见 3.6。

### 3.4 回复起草（`src/lib/agent/reply.ts`）

1. `extractOfferCents` 从消息里抠出买家报价，只接受与挂牌价同量级的数字
   （所以「电池健康 92」不会被当成出价）；
2. `classifyIntent` 按关键词 + 报价判定意图：售后 > 催发货 > 议价 > 咨询细节 > 问库存 > 其他；
3. `draftReply` 按意图生成草稿：
   - 议价：出价 ≥ 底线就接受，否则还价到 `max(底价, 挂牌价 × (1 − 让价上限))`；
   - 催发货：引用真实订单与运单号；
   - 问库存：按真实库存回答，卖完了就说卖完了；
   - 咨询细节 / 售后：标记 `needsHumanEdit`，强制人工确认。

全流程零模型依赖。配置了 `OPENAI_API_KEY` 时再叠一层口语化润色，失败静默回落。

### 3.5 自动巡检与失败处理（v1.1）

只会在你点按钮时才动的 Agent 只能算半个 Agent，所以 v1.1 补了两件事：

**后台巡检。** `src/instrumentation.ts` 在服务端启动时拉起 `scheduler.ts` 里的定时器，
每 30 秒问一次 `shouldRunScheduledTick(state, now)`（纯函数，可测）。到点了就走
`performTick(state, now, "scheduled")` —— 和点按钮完全同一条路径，行为不会分叉。

两个细节：

- 还没跑过时从 `seededAt` 起算，所以刚打开应用时队列是空的，第一轮仍然由人触发；
- 间隔填 0 或关掉开关都不会跑，避免手滑把它变成死循环。

定时器用 `unref()`，不会拖住进程退出；全局变量兜底，开发模式反复热重载也只有一个。

**失败不再消失。** 自动执行失败的动作以前只是个字符串塞进返回值里就没了。现在会
以 `failed` 状态留在队列里，带着平台返回的原因和尝试次数，在「执行失败」标签页里
可以原样重试或者改完再试，总览页顶部也会横一条提示。

### 3.6 安全阀（v1.2）

接真实账号之前，风险最大的不是「规则判断错了」，而是「判断对了但执行失控」。
所有写操作现在都穿过 `GuardedAdapter`，顺序固定：

```
急停？ → 写模式？ → 限流？ → 真正执行 → 记账（风控 / 连续失败 → 自动急停）
```

- **写模式** 有三档：本地模拟（改本地数据）、演练（只记录不执行）、真实写入（未接入，选了会被拒绝）。
- **限流** 是滑动窗口 + 最小间隔，只在非模拟模式生效 —— 本地模拟没有账号需要保护。
- **风控自动暂停**：通道返回 `riskControl` 标记就立刻急停。撞上滑块还继续重试，只会让账号更危险。
- **连续失败熔断**：连续失败到阈值自动急停，成功一次清零。

一个设计取舍值得记下来：被急停或限流拦下的动作**不会**变成失败项，而是这一轮直接跳过。
状态没变，下一轮自然会重新提出来 —— 比塞进失败队列让人手动重试干净得多。

**底价确认**是配套的一条：从平台同步进来的商品只有挂牌价，底价是按九折估的，
标成 `floorConfirmed: false`。在人确认之前自动降价规则会绕开它 ——
拿一个猜出来的底价去降价，等于没有底价。

- [x] 自动巡检到点会自己跑，没到点不会跑，关掉就永远不跑

- [x] 急停之后任何写操作都进不去，演练模式下数据一个字节都不变
- [x] 限流按窗口和间隔生效，被拦下的动作不会变成失败项
